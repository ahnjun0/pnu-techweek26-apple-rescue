## Phase 1 — 오도메트리

**만든 것**: `sensors.py`, `localization.py`, `debug/odometry_check.py`

**나침반 공식은 유도하고 실증했다**
`compass.md:164`(ENU 에서 북=+y) + `compass.md:142`(북쪽 벡터를 디바이스 좌표계로)
→ R(−θ)·(0,1) = (sin θ, cos θ) → **θ = atan2(v[0], v[1])**
> 문서의 bearing 예제는 `atan2(north[1], north[0])` 로 인수 순서가 반대다.
> 그건 "북쪽 기준 시계방향 방위각" 이라 우리 규약과 다르다.

실증: GPS 이동방향 +0.00° vs 나침반 +0.00° (차이 0.00°)

**측정 결과**

| θ 소스 | 정사각형 완주 후 위치 오차 |
|---|---|
| compass | **0.07 cm** |
| gyro | **0.07 cm** |
| encoder only | 6.12 cm |

**발견 1**: GPS 가 `extensionSlot`(로봇 기준 −0.03, 0, 0.153)에 달려 3 cm 오차가
섞였다. 보정 수식으로 숨기지 않고 **GPS 를 로봇 원점에 정확히 놓았다.**

**발견 2**: 유효 축간 거리 ≠ 기하학적 축간 거리. 엔코더 전용 각도가 360° 회전에서
40° 부족했다 (타이어 폭·미끄러짐). `0.16 × 360.31/319.93 = 0.180` 으로 보정하니
오차 44.43 → 6.12 cm.

## Phase 2 — LiDAR 방향 실측, 매핑

**만든 것**: `debug/lidar_orientation.py`, `worlds/lidar_test.wbt`, `mapping.py`,
`viz.py`, `controllers/teleop`

**LiDAR 방향은 추측하지 않고 쟀다**
상자를 정면 1.0 m / 왼쪽 1.5 m / 오른쪽 2.0 m 에 놓고 인덱스를 역산:
```
정면 = 인덱스 180,  왼쪽 = 90,  오른쪽 = 270
⇒ 인덱스 0 은 로봇 뒤쪽,  인덱스가 늘면 시계 방향
검산(공식에 안 쓴 오른쪽 상자): 예측 −90.00° vs 실제 −90° (차이 0.00°)
```
> 문서 그대로 `OFFSET=0, SIGN=+1` 로 추측했다면 지도가 180° 돌고 좌우가 뒤집혔다.

**매핑 버그**: 1 m 거리에서 이웃 광선 간격은 1.75 cm 로 셀(5 cm)보다 작다.
같은 스캔 안에서 옆 광선이 방금 찍은 벽을 "빈 칸" 으로 덮어썼다.
→ 통과 칸과 맞은 칸을 따로 모았다가 **"한 스캔 안에서는 맞은 칸이 이긴다"** 로 수정.

**월드 버그**: W2(x=1)와 W3(y=0)가 만나 오른쪽 위 방이 **완전히 밀폐**돼 목표물 2번에
갈 수 없었다. → `tests/test_world_geometry.py` 가 flood fill 로 영구 검사한다.

## Phase 3 — A* 와 프론티어

**만든 것**: `planner.py`, `exploration.py`, `debug/plot_planner.py`, 테스트 149개

**설계 결정**: 대각선은 **양옆이 둘 다 열려야** 허용 (한쪽만 막혀도 금지).
이미 팽창까지 해 놓고 굳이 모서리를 스칠 이유가 없다.

**범용성을 테스트로 고정**: 해상도 0.025/0.05/0.10, 비정사각형 지도,
로봇 반경 3종. 같은 문이라도 큰 로봇은 거부하고 작은 로봇은 통과하는지까지.

**테스트가 잡은 버그**
1. `inflate` 가 장애물이 없으면 조기 반환해 지도 테두리를 안 막았다
2. 로봇이 벽에 붙으면 영영 못 움직였다 → 주변에서 "진짜 벽이 아닌 칸만" 뚫어 준다

**성능**: inflate 0.6 ms, 최악 A* 7.8 ms, 프론티어 0.5 ms (틱 예산 32 ms)

## Phase 4 — 주행과 상태 머신

**만든 것**: `follower.py`, `mission.py`, `tests/fake_world.py`(레이캐스팅),
`debug/mission_check.py`

**가짜 월드가 GUI 없이 잡아낸 버그 5개**
1. **경로 축약 때문에 모퉁이를 잘랐다.** `lookahead_point` 가 꼭짓점만 보니
   "2 m 앞 점" 으로 직진해 경로 모양을 무시했다 → 선분 위를 따라가도록 수정 → 충돌 0
2. **정지거리(0.32) > 계획 여유(0.21)** 모순 → 멀쩡한 경로에서 얼어붙었다
3. **정지 중 회전까지 막고 있었다** → 비스듬히 걸리면 방향을 못 고쳤다
4. **유령 프론티어** (벽 구멍 옆) → "실제로 설 수 있는 칸" 만 프론티어로
5. **`viz.update` 가 틱 예산 전체(32 ms)** → 헤드리스에서 끄니 0.19x → 1.5x

**Webots 에서만 드러난 것**: 보행자가 로봇을 **벽 속 0.08 m 까지 밀어 넣었다.**
그 상태에선 회전조차 막혀 같은 명령을 260초 반복했다.
→ 탈출은 **항상 병진을 포함**해야 한다.

## 계획기 비교 — A* vs D* Lite

→ 자세한 내용은 `docs/계획기-비교-Astar-vs-DstarLite.md`

결론: **목표가 계속 바뀌는 프론티어 탐색에는 A* 가 맞다.** D* Lite 는 목표를
고정해 놓고 재사용하는 구조라 목표가 바뀔 때마다 제일 비싼 첫 풀이를 반복한다.
다만 목표가 오래 고정되는 RETURN/APPROACH 구간과 큰 맵에서는 유리하다.

## Phase 5 — 목표물 탐지와 다중 목표

**만든 것**: `detect.py`, `mission.py` 의 APPROACH/SWEEP/RETURN,
`worlds/camera_test.wbt`, `debug/camera_lidar_check.py`

**색 임계값을 측정으로 정했다**
```
진짜 목표물 픽셀 S 중앙값 208   /   오검출된 바닥 S 중앙값 118 (90퍼센타일 131)
⇒ DETECT_SAT_MIN = 150 (두 분포 사이)
결과: 바닥 오검출 29.9% → 0.0%, 빨간 덩어리 5개 = 실제 빨간 물체 5개
```

**카메라 방위각 부호도 실증**: 왼쪽에 둔 기둥 실제 +22.9° vs 측정 +22.9°.
> 처음엔 "뒤집혔다" 고 나왔는데, 대조용 기둥을 화각(±28.5°) **밖**(+33.7°)에 둔
> 제 실수였다. 진단 도구 자체를 먼저 의심해야 했다.

**LiDAR 의 구조적 한계를 실증**: 높이 0.10 m 물체, 공중에 뜬 물체, 3.5 m 밖 물체는
카메라에만 보인다. `detect.py` 는 "봤지만 거리를 모른다" 를 정상으로 다룬다.

**SWEEP 상태를 추가한 이유**: LiDAR 는 360° 를 보지만 카메라는 57° 만 본다.
지도를 다 그려도 목표물 쪽을 한 번도 안 봤을 수 있다 (실제로 3개 중 2개만 찾았다).
탐색이 끝났는데 목표물이 모자라면 몇 곳에서 제자리 한 바퀴를 돈다.

**상태 전이를 한 곳으로 모았다**: 판단이 세 군데 흩어져 있어 SWEEP 이 세 번째
목표물을 찾고도 방문하지 않고 복귀해 버렸다. `_decide_next()` 하나로 통합.

**월드 설계 교훈**: 보행자 경로를 목표물 옆에 두면 안 된다.
목표물 1번(−2.2, 1.8) 옆으로 보행자를 지나가게 했더니, 접근 중에 벽과 보행자 사이에
끼여 물리 엔진이 로봇을 58만 km 밖으로 날려 보냈다.

## 추가 라운드 — GUI 로 보면서 잡은 것들

사용자가 GUI 로 직접 보고 지적한 증상 셋을 추적해 원인을 찾았다.
셋 다 **내 첫 가설이 틀렸고**, 기록(`debug/out/trace.csv`, `grid.npz`)을 뒤져서야
진짜 원인이 나왔다.

| 사용자가 본 것 | 내 첫 가설 | 실제 원인 |
|---|---|---|
| 경로가 벽을 뚫는다 | 벽에 구멍이 났다 | 벽 *위로* 넘어 아레나 밖을 돌았다. 지도가 아레나보다 크고 바깥이 전부 미지라 A* 에게는 벌판이었다 |
| 우상단에서 버벅인다 | 좁은 문을 못 지난다 | 목표물 0.58 m 앞에서 판정 0.57 m 를 1 cm 차로 못 넘겨 31초를 서 있었다 |
| 우상단 진동 | DWA 채터링 | LiDAR 가 한 틱만 튀어(70cm → 13cm → 70cm) "눌렸다" 로 믿고 1초씩 후진했다. 40초 동안 15번 |

**교훈**: 증상에서 원인을 추측하지 말고 매 틱 기록을 남겨 두고 뒤질 것.
`trace.csv` 가 없었으면 셋 다 못 찾았다.
