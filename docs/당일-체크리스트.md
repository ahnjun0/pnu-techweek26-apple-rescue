## 1. 먼저 재고 나서 고친다

```bash
./run_headless.sh worlds/<대회월드>.wbt 1100     # 한 번 돌려 요약을 본다
```

요약에서 **이 순서로** 본다:

1. `찾은 목표물 : N 개` — 채점 기준 1번. 이게 최우선이다
2. `❌ 충돌했다` / `닿아 있던 시간` — 채점 기준 2번
3. `시간이 어디로 갔나` — 전진 0 이 20% 넘으면 주행기 문제다
4. `사람 검출 성적` — **헛것보다 놓침이 비싸다** (헛것=돌아감, 놓침=충돌)
5. `탐색 진도` — 90% 까지 얼마나 걸렸나

## 2. 증상별 처방 (오늘 실제로 겪은 것들)

| 증상 | 원인 | 고칠 곳 |
|---|---|---|
| 한자리에 수백 초 | 못 가는 목표를 계속 고름 | `exploration.choose` 의 도달 가능성 — `plan()` 은 목표를 몰래 바꾼다 |
| "도착" 인데 목표에 못 감 | `planner.nearest_free` 대체 | 도착 판정을 **원래 목표** 로 |
| 좁은 문 앞에서 교착 | 비상구가 `safe.any()` 로 걸려 안 열림 | "안전한 **전진** 후보가 없을 때" 로 |
| 시간의 절반이 전진 0 | 속도 0 후보가 여유 점수 만점 | `DWA_IDLE_PENALTY` (가중치 합보다 크게) |
| 갈 데 남았는데 복귀 | 문지기가 `choose()` 와 다른 논리 | `_frontiers_remain` 이 `choose()` 에 직접 묻게 |
| 사람 없는데 사람 검출 | 벽 표면 양자화 잡음 | `PEOPLE_WALL_CLEARANCE` |
| 목표물을 보고도 복귀 | 25회 미만은 판단에 안 보임 | 미확정 후보 확인하러 가기 |

## 3.5 "최적보다 3배나 가는데?" — 정상이다

`debug/teacher.py` 가 내는 숫자는 **지도를 다 아는** 로봇의 최적 경로다.
우리 로봇은 지도를 모른 채 시작하므로 따라잡을 수 **없다** — 이론적으로 그렇다.

**online graph exploration** 문헌:
- **하한 4배**: 어떤 알고리즘도 최악의 경우 최적의 4배보다 잘할 수 없다 (증명됨)
- **상한**: 일반 그래프에 상수 보장은 **1994년부터 미해결**. 평면 그래프는 16배 보장

```
이론 하한        4배
평면 최선 보장  16배
우리           1.11 ~ 3.89배   ← 하한보다도 낮다
```

→ **거리 배수를 낮추려고 튜닝하지 마라.** 배수가 낮은 것은 목표물이 경로에 우연히
   잘 놓인 **운** 일 수 있다 (같은 지도에서 시작점만 바꿔 3.5배 흔들린 적 있다).
   볼 것은 **최악의 경우에도 목표물을 찾는가** 다.

## 5. 절대 하지 말 것

- **결과가 비트 단위로 같은데 "효과 없음" 이라고 읽기.** 소수점까지 동일하면
  효과가 없는 것이 아니라 **코드가 안 돈 것** 이다. 오늘 세 번 나왔고 세 번 다
  배관이 끊겨 있었다 (`choose_unseen` 의 훅 위치, 시간 예산의 훅 위치,
  `camera_seen` 인자 미전달). 세 번째는 **Webots 10회·2시간** 을 버렸다.
  → **새 기능을 넣으면 먼저 "숫자가 바뀌는가" 만 1회로 확인한다.** 바뀌지 않으면
     값을 바꾸지 말고 **호출 경로를 찍어 본다.**
- **계산을 늘리면서 비용을 안 재기.** 오늘 두 번 당했다:
  복귀 마감에 매 틱 A\* 를 넣어 시뮬레이션이 절반 속도(900초 -> 580초),
  사람 예측을 모든 검출에 걸어 comb0/comb2 가 완주 실패(1100초에 680초까지).
  → **새 계산을 넣으면 그 자리에서 `실제 대기 Ns (상한 Ms)` 를 확인한다.**
- **검출 유무로 안전장치를 켜고 끄기.** 검출기는 완벽할 수 없다. 조건은
  **거리·속도 같은 물리량** 이어야 한다. 오늘 세 번 같은 처방을 썼다:
  `allow_idle`(0.8 m), 사람 예측(1.28 m), 유령 사람(움직임 기준).

- **측정 없이 값 바꾸기.** 오늘 그렇게 넣은 것 넷 중 셋을 되돌렸다
- **실행 중 코드 바꾸기.** 그 측정은 버려야 한다
- **사람 있는 월드를 1회로 판단하기.** 보행자가 밀어서 결과가 크게 흔들린다. 3회 중앙값
- **`plan()` 이 참이라고 갈 수 있다고 믿기.** 도달 가능성은 `exact=True` 로 묻는다

## 계측기를 먼저 의심한다

지표가 실패를 가리키면, 고치기 전에 **그 지표가 무엇을 재고 있는지** 본다.

- **"실행 전체의 최솟값" 은 이상치 하나에 끌려간다.** 충돌 판정이
  `min(LiDAR) - ROBOT_RADIUS` 였는데, LiDAR 는 0.12 m 에서 포화하고
  ROBOT_RADIUS(0.13)는 계획용 패딩값이라, 허위 광선 **하나** 가 16월드 중 10개를
  "충돌" 로 뒤집었다. 실제로는 한 번도 닿지 않았다.
- **충돌은 LiDAR 로 판정할 수 없다.** 몸체 외접 반경 0.110 m 는 센서 최소거리
  0.12 m 보다 작고, LiDAR 는 원점보다 3 cm 뒤에 있다. 진짜 위치와 기하로 잰다.
- **결과가 비트 단위로 같으면 "효과 없음" 이 아니라 코드가 안 돈 것이다.**
- **잘린 것과 실패한 것을 구별한다.** `run_headless` 가 컨트롤러 크래시를 못 보고
  상한까지 기다린 적이 있다 (1400초 낭비). 로그에 `controller crashed` 를 본다.

## 로봇이 다른 기종일 때 — 30분 부트스트랩

질의응답은 *"단순한 Differential Drive 로봇, IMU 는 없고 그 기능을 구성하는 센서들이
따로 탑재"* 라고만 했다. **TurtleBot3 Burger 라는 보장은 없다.**

다행히 `config.py` **밖에** 박힌 로봇 상수는 없다 (규칙 3). `mapping` / `planner` /
`exploration` / `follower` / `common` 은 순수 numpy 라 **그대로 쓴다.**

바꿀 것은 아래뿐이고, 순서대로 한다:

| 순서 | 할 일 | 얻는 값 |
|---|---|---|
| 1 | Webots Scene Tree 를 눈으로 본다 | 장치 이름 9개 (`LEFT_MOTOR_NAME` …) |
| 2 | `debug/lidar_orientation.py` | `LIDAR_ANGLE_OFFSET`, `LIDAR_ANGLE_SIGN` |
| 3 | `debug/odometry_check.py` | `WHEEL_BASE_ODOM`, 나침반 규약 |
| 4 | `debug/lidar_min_range.py` | `LIDAR_MIN_RANGE`, 센서 오프셋 |
| 5 | PROTO 를 읽는다 | `WHEEL_RADIUS`, `MAX_WHEEL_SPEED`, `ROBOT_BODY_RADIUS` |
| 6 | `pytest` + `./check_rules.sh` | 순수 알고리즘이 안 깨졌는지 |
| 7 | `MISSION_TIME_LIMIT` 을 당일 제한으로 | (로봇과 무관하지만 같이 놓치기 쉽다) |

### ⚠️ 문서만 보고 정하면 틀리는 셋

- **유효 축간거리** — 기하값 0.16 이 아니라 실측 **0.180** 이었다 (12% 차이).
  360° 회전을 시켜 재야 한다.
- **LiDAR 인덱스 방향** — 인덱스 0 이 로봇 **뒤쪽**, 증가 방향이 **시계**였다.
  문서로 확정하지 말고 상자 3개로 실험한다.
- **센서 최소거리와 오프셋** — LiDAR 가 원점보다 0.0278 m 뒤에 있고 0.12 m 에서
  포화한다. 이것을 모르면 충돌 판정이 통째로 거짓이 된다 (그 함정에 한 번 빠졌다).

### 출발 위치를 모를 때

`START_X/Y` 는 GPS 가 아니라 **좌표계 원점 선언** 이다. 다만 지도가 월드 원점 중심의
고정 격자(지금 8×8 m)이므로, 출발점이 어긋나면 지도 창이 아레나에서 밀려난다.
→ 출발 위치를 모르면 `START = (0, 0)` 으로 두고 **지도를 12×12 m 로 넓힌다**
  (8×8 이면 최악의 경우 여유가 1 m 뿐이다).

### 속도가 다를 때 (중요)

**"찾기" 는 속도에 강하고, "자기 위치를 아는 것" 은 약하다.**

- 검출: 확정 문턱 25회인데 4배속에서도 78 프레임을 얻는다 → 안 깨진다.
- 위치 추정: 스캔매칭 갱신 사이 이동량이 4배속에서 보정 범위의 **102%** 가 된다
  (1배속은 26%). 넘으면 못 따라잡는다.
- 실측: 속도를 0.08 → 0.2 m/s 로 올린 순간 corridor2 에서 위치가 **1.45 m** 틀어져
  지도가 망가지고 62초에 0/3 으로 끝났다. 로봇이 **자기 지도를 앞질렀다.**

→ 로봇이 더 빠르면 `SCANMATCH_EVERY` / `MAP_UPDATE_EVERY` / `DETECT_EVERY` 를
  **틱 수가 아니라 이동 거리 기준으로** 줄여야 한다.
