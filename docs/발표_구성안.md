## 1. 무엇을 따랐나 (출처)

발표 순서를 우리가 새로 짜지 않았다. 세 선행 자료를 역할별로 나눠 따른다.

| 역할 | 출처 | 우리가 가져온 것 |
|---|---|---|
| **전체 뼈대** (무엇을 어떤 순서로) | Thrun et al., *Stanley: The Robot that Won the DARPA Grand Challenge*, Journal of Field Robotics 23(9):661–692, 2006. DOI 10.1002/rob.20147 | 로봇 시스템 발표의 표준 순서: 과제·규칙 → 차량 → 소프트웨어 구조·설계 원칙 → 상태 추정 → 지도 → 비전 → 경로 계획 → 제어 → **개발 과정과 레이스** → 논의 |
| **"왜 그 기준인가" 를 말하는 틀** | 같은 논문 5.2절 *Data-Driven Parameter Tuning* | 문제를 **숫자로** 보이고("12.6% of known drivable area is classified as obstacle") → 방법 → **측정으로 확인**("drops from 12.6% to 0.002%") |
| **발표 방식** | Simon Peyton Jones, John Launchbury, John Hughes, *How to give a great research talk* (Microsoft Research, 슬라이드 2016) | 동기 20% / 핵심 아이디어 80%, 첫 2분에 문제를 말한다, 시작에 목차 금지, **예시가 주무기**, 기술 세부는 빼고 백업 슬라이드로, 질문은 기회 |
| **시작과 끝** | Patrick Winston, *How to Speak* (MIT OCW RES.TLL-005, IAP 2018) | 농담이 아니라 **약속(empowerment promise)** 으로 시작, 핵심을 반복(cycling), 비슷하지만 다른 것과 **선을 긋기**(near miss / fence), 첫 5분에 비전·한 일·단계, **마지막 장은 "기여(contributions)"** — "질문 있으신가요?" 로 끝내지 않는다 |

**선택 이유**: Stanley 논문은 우리와 같은 문제(센서 → 위치 추정 → 지도 → 계획 → 제어, 그리고 대회)를 다룬 가장 널리 인용되는 시스템 보고서다. 특히 3.1.4절이 우리 방식과 같다 — "all data are logged. By using a special replay module, the software can be run on recorded data." 우리도 녹화 재생 도구(`debug/replay_localization.py`)로 판단을 검증했다.

## 2. "AI 가 하라는 대로 했구나" 로 보이지 않으려면 — 모든 결정을 같은 5단 틀로

Stanley 5.2절의 틀을 우리 결정 하나하나에 똑같이 적용한다. **슬라이드마다 이 다섯 칸이 있어야 한다.**

| 칸 | 내용 | 없으면 생기는 인상 |
|---|---|---|
| ① **관찰** | 언제, 어디서, 무엇이 잘못됐나 (시각·좌표·로그 숫자) | "그냥 좋다니까 넣었다" |
| ② **가설** | 원인이 무엇이라고 봤나 | "원인은 모르고 고쳤다" |
| ③ **기각한 대안** | 다른 방법을 무엇을 해 봤고 왜 버렸나 (숫자) | "처음 떠오른 걸 했다" |
| ④ **기준값의 출처** | 문턱값이 **물리량** 또는 **측정 분포** 중 어디서 왔나 | "숫자를 아무렇게나 골랐다" |
| ⑤ **확인과 남은 한계** | 고친 뒤 측정 결과, 그리고 여전히 안 되는 것 | "과장한다" |

그리고 **사람이 관찰한 것을 사람이 관찰했다고 말한다.** 오늘 핵심 발견의 상당수는 팀이 GUI 를 보다가 짚은 것이다 (아래 표). 이것이 "시킨 대로 한 것" 과 "문제를 보고 판단한 것" 을 가르는 가장 강한 증거다.

| 팀이 GUI 에서 짚은 것 | 거기서 나온 결정 |
|---|---|
| "LiDAR 가 360° 인데 왜 제자리에서 한 바퀴 도나?" | 시작 스캔의 설명이 틀렸음을 인정하고 다시 쟀다 — 끄면 12/12 → 11/12 라 남기되, 이유가 "지도"가 아니라 "카메라 60°" 일 수 있음을 기록 |
| "카메라에 분명히 보였는데 왜 그쪽으로 안 가나?" | 카메라 검출을 프론티어보다 우선하도록 순서를 바꿈 |
| "문 앞에서 부르르 떨고, 세 번이나 그 방에 들어가려 한다" | 문 한가운데 15 cm 가짜 벽을 찾음 → 지나온 길 되짚기 복귀 |
| "카펫에서 오차가 67.8 cm 로 확 뛴다" | 나침반 회전 vs 바퀴 회전 비교(미끄러짐 감지), 바퀴 반지름 바닥 보정 |
| "사과를 계속 치고 다닌다" | 사과가 LiDAR 평면보다 낮다는 것을 확인 → 카메라로 낮은 물체를 계획 지도에 |
| "소화기를 계속 방문한다" | 크기 거리 vs 바닥 거리의 일치 검사, 세로/가로 비율 |

## 3. 발표 순서 (Stanley 뼈대 + 발표 방식 규칙)

시간은 10분 기준 비율이다. 발표 시간이 다르면 비율만 유지한다. 괄호 안은 Stanley 논문의 대응 절.

### 3.0 시작 — 30초 (Winston: 약속으로 시작, 목차 금지)

> "이 발표가 끝나면, 절대 위치 없이 바퀴와 나침반과 LiDAR 만으로 로봇이 **자기가 어디 있는지 얼마나 틀리는지를 스스로 알아채는** 방법 — 그리고 우리가 그 기준 숫자 하나하나를 어떻게 정했는지 — 를 보시게 됩니다."

- 제목 슬라이드에 팀원 이름 (Peyton Jones: 공저자는 제목에서 밝힌다).
- **목차 슬라이드는 두지 않는다** ("Outline of my talk: conveys near zero information at the start").

### 3.1 동기 — 2분 (§1 Introduction, §1.1 Race Rules) — Peyton Jones: 20%

첫 2분에 네 질문에 답한다 ("Why should I tune into this talk? What is the problem? Why is it interesting? Does this talk describe a worthwhile advance?").

- **과제와 규칙** 을 한 장으로: 모르는 집, 빨간 사과 2개, 복귀, GNSS·절대 위치 금지, 속도 한계.
- **왜 어려운가를 숫자 하나로**: "첫 완주에서 로봇은 소화기를 사과로 알고 방문했고, 빨간 사과는 0/2 였다."
- 🎞 **GIF 1: 전체 주행 타임랩스** (시작 → 사과 2개 → 복귀). Winston 의 "첫 5분에 '해냈다'를 보인다"에 해당한다.

### 3.2 핵심 아이디어 한 문장 — 30초 (§3.1 Design Principles)

Stanley 는 설계 원칙을 한 문장으로 내세웠다 — "Treat autonomous navigation as a software problem." 우리도 하나만 말하고 발표 내내 반복한다(Winston: cycling).

> **"모든 문턱값은 측정에서 왔고, 켜서 나빠진 기능은 뺐다."**

근거 한 줄: 해 보고 뺀 것들의 기록(`docs/무엇을-빼기로-했나.md`)이 있다. 이 문장을 각 절 끝에서 다시 말한다.

### 3.3 로봇과 센서 — 30초 (§2 Vehicle)

한 장 표: 엔코더·나침반·LiDAR(360°, 평면 1층, 바닥에서 약 17 cm)·카메라(60°). **"LiDAR 는 17 cm 높이의 평면만 본다"** 를 여기서 말해 둔다 — 뒤의 카펫(2 cm)·사과(지름 10 cm) 문제의 복선이다.

### 3.4 소프트웨어 구조 — 1분 (§3.2 Processing Pipeline)

파이프라인 그림 한 장 (`발표_기술해설.md` 0장). 한 틱 = 64 ms 의 순서. 그리고 **개발 방식** 을 여기서 말한다 (Stanley §3.1.4):

- 모든 실행을 녹화한다 (`tape.npz`: 스캔·추정 위치·정답 위치).
- 녹화를 Webots 없이 재생해 방법을 바꿔 끼워 본다 → 같은 주행에서 공정하게 비교.
- 정답 위치는 **채점 전용** 월드 사본에서만 읽는다 (주행 코드에는 없다 — 자동 검사).

### 3.5 핵심 기술 — 5분 (§4~§9) — Peyton Jones: 80%, 예시가 주무기

Peyton Jones: "Narrow, deep beats wide, shallow." 모든 모듈을 고르게 말하지 않는다. **결정의 근거가 가장 뚜렷한 세 가지** 를 깊게, 나머지는 한 줄로.

#### (A) 위치 추정 — "로봇이 자기 오차를 알아채게" (§4 State Estimation) — 2분

| 칸 | 내용 |
|---|---|
| ① 관찰 | 복귀했다고 판단했는데 **실제로는 시작점에서 1.99 m** 모자랐다. 팀이 GUI 에서 "카펫에서 오차가 확 뛴다" 를 발견 |
| ② 가설 | 방향은 나침반(절대 방위)이라 안 틀어진다 → 틀어지는 것은 **거리**. 두 원인: (a) 바닥 탓 일정 비율 오차, (b) 카펫 턱 미끄러짐 |
| ③ 기각한 대안 | 스캔 매칭을 켜기만 → 오차 21 → 164 cm, 사과 1 → 0 (덮어쓰기 방식이 원인으로 봄). 벽 근처 비용 기울기 → 오차 951 cm |
| ④ 기준값의 출처 | (a) 직진 38구간의 "바퀴 거리/실제 거리" 중앙값 **0.983** (범위 0.976~0.988) → 반지름 0.033/0.983. 빈 월드는 64 ms 에서도 1.002 → 물리 주기 탓이 아님을 배제. (b) 명령 회전 대비 나침반 회전: 평소 **0.87~1.14**, 카펫 턱 **0~0.3** → 문턱 0.6 rad/s, 0.3초 |
| ⑤ 확인·한계 | (a) 보정 후 비율 **1.0015**. (b) 녹화 재생에서 카펫 사건과 185 cm 튐을 모두 감지. **실제 주행 점수 개선은 아직 측정 중** — 그래서 기본값 꺼짐 |

🎞 **GIF 2: 카펫 턱 미끄러짐** (302~308초 구간 — 로봇은 제자리 회전을 명령하는데 턱을 따라 옆으로 밀려간다).
**선 긋기(near miss)**: "이건 벽에 끼어 헛도는 것과 다릅니다. 헛돌면 제자리인데 추정이 앞으로 가고, 이건 **추정은 제자리인데 몸이 옆으로 갑니다.**" — 그래서 기존 끼임 감지(추정 위치 기준)로는 못 잡는다.

#### (B) 사과 인식 — "가짜를 하나씩 이름 붙여 걸렀다" (§6 Computer Vision) — 1.5분

Stanley 5.2절처럼 **오탐률을 숫자로** 보이는 절이다.

| 가짜 | 관찰 | 걸러낸 기준 | 기준의 출처 |
|---|---|---|---|
| 가까운 소화기 | 첫 완주에서 사과로 확정·방문 | 크기로 잰 거리 vs 바닥으로 잰 거리 **30% 이내** | 진짜 사과 1~7% 어긋남, 소화기 81% (녹화) |
| 먼 소화기 | 195초에 다시 방문 (4.6~5.2 m, 23×72 px) | 세로/가로 **≤ 1.5** | 거리 차 29% 로 위 검사를 통과한 사례. 사과는 1.0~1.2 |
| 누운 캔 | 사람 검출을 켠 실행마다 방문 | 세로/가로 **≥ 1/1.5** | 캔 26×11 = 0.42 |
| (예비) 병·컵 | — | YOLO 가 bottle·cup 이면 버림 | 사과 23장 중 23장 sports ball, 캔은 사과 계열 0장 |

- 녹화 668장 재판정: 소화기 오탐 10 → 0, YOLO 는 24장에서만 동작.
- **선 긋기**: YOLO 를 "문지기"로 쓰지 않은 이유 — 멀리 있는 사과는 YOLO 가 자주 놓쳐서(초기 측정에서 빨간 픽셀과 겹친 검출 3장뿐), 문지기로 쓰면 사과를 잃는다. 그래서 **거부권** 으로만 쓴다.
- 🎞 **GIF 3: 카메라 오버레이** — 소화기가 보이는데 확정되지 않고 지나가는 장면.

#### (C) 보행자 — "도망이 아니라 예측" (§7~§8) — 1분

| 칸 | 내용 |
|---|---|
| ① 관찰 | 사람 검출을 끈 실행에서 보행자와 **3.8초** 닿음 |
| ② 가설 | 월드 파일: 보행자 `--speed=0.2` = **로봇 최고 속도와 같다**. Webots 보행자는 로봇을 피하지 않는다 → 도망은 불가능, 갈 곳을 예측해야 한다 |
| ③ 기각한 대안 | 연습 월드(사람 없음)에서 사람 검출을 켜면 **헛것 100%** (maze0 에서 3,237회) → 연습 월드에서는 끔. 두 스캔 차이로 낸 속도는 잡음(위치 오차 23 cm)이 사람 속도보다 컸다 |
| ④ 기준값의 출처 | 칼만 필터 측정 잡음 $\sigma_z = 0.23$ m = 실측 위치 오차. 예측 1.2초 = DWA 가 굴려 보는 시간과 같게 |
| ⑤ 확인 | 접촉 3.8초 → **0초** (사람 검출 350초, + 칼만 342초) |

🎞 **GIF 4: 보행자와 교차** — 로봇이 멈추거나 비켜서 보행자를 먼저 보내는 장면.

#### 나머지는 한 줄씩 (Peyton Jones: "omit technical details… have backup slides")

- 지도: log-odds 베이즈 갱신 — 벽은 한 번 맞으면 막힘, 지우려면 14번.
- 탐색: 프론티어 중 **A\* 경로가 가장 짧은 곳** 하나만. 점수를 여러 겹 섞었을 때 월드마다 들쭉날쭉해서 뺐다 (연습 16월드 46~48/48).
- 계획: 벽을 0.35 m(몸 0.13 + 안전거리 0.22) 부풀린 A\*. 제어: DWA 119 후보, 두 바퀴 같은 비율로 속도 제한.
- 복귀: 지도에 길이 없으면 **지나온 길을 되짚는다** — 🎞 **GIF 5**: 가짜 벽에 막힌 방에서 되짚어 나오는 장면 (447초 시간 초과 → 297.6초 복귀).

### 3.6 실제 시연 — Webots 라이브 (§10 Development Process and Race)

Stanley 는 레이스 결과를 "무엇이 일어났고 어디서 느려졌나" 로 보고했다 (§10.3, 예: "During 68.2% of the course…"). 시연도 같은 태도로 한다.

- **무엇을 보여 줄지 미리 말한다**: "지금부터 볼 것은 ① 사과를 확정하는 순간 ② 보행자 앞에서 멈추는 순간 ③ 복귀입니다."
- 전체 주행은 약 7분(433초)이라 발표 시간 안에 다 보여 줄 수 없다. 발표 시작 때 실시간으로 켜 두고 이 순서에 맞춰 화면을 돌리거나, 결정적 장면은 GIF 로 대신한다.
- **라이브가 실패할 때를 대비한다** (Peyton Jones: "Laptops break: leave a backup copy"): 같은 설정의 녹화 GIF 를 백업으로. 시뮬레이션은 결정적이라 같은 설정이면 같은 장면이 나온다 — 이 사실 자체가 재현성의 증거다.

| + 사람 검출·칼만 | 1/2 (+캔 오탐) | 0초 | 성공 |
| + 모양 검사·YOLO | **2/2** | 0초 | 로봇은 성공 판단, **실제로는 1.99 m 모자람** |

**한계는 우리가 먼저 말한다** (Peyton Jones: 질문은 기회 / 과장하지 않는다):
1. 복귀 정확도: 카펫 미끄러짐이 몇 번 일어나느냐가 경로에 따라 운이다.
2. 스캔 매칭: 녹화 재생에선 오차 186 → 21 cm 지만, 실제 주행 점수 개선은 아직 확인 못 해 꺼 두었다.
3. 측정 표본: 월드 하나, 실행 한 번씩이다.

### 3.8 끝 — 기여 슬라이드 (Winston: "questions?" 로 끝내지 않는다)

**기여(Contributions)** — 마지막 장은 이것만 띄워 두고 질문을 받는다.

1. 절대 위치 없이, **나침반 대 바퀴** 비교로 로봇이 자기 미끄러짐을 알아챈다.
2. LiDAR 없이 **카메라 한 장으로 거리를 두 번 재서** 사과와 가짜(소화기·캔)를 가른다.
3. 보행자와 **속도가 같은** 상황에서, 칼만 필터 예측으로 접촉 0초.
4. 모든 문턱값에 **측정 출처** 가 있고, 켜서 나빠진 기능은 기록과 함께 뺐다.

그리고 3.0의 약속을 지켰음을 한 문장으로 확인한다 (Winston).
